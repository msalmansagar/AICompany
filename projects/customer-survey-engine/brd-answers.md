## OQ-05 — Source tables and fields

| | Applications | Disbursements | Fund Transfer |
|---|---|---|---|
| Table | `qdb_loan_application` | `qdb_payment_authorization_ticket` | `qdb_cheque_clearing` |
| Customer | `qdb_customerid` (Account lookup) | `qdb_Customer_Name` (lookup) | `qdb_CIF_No` (lookup) |
| Type | `qdb_LoanAppl_Type` | `qdb_disbursement_type_1` (option set) | `qdb_Type` |
| Submitted | no flag; identified by `statuscode` | no flag; identified by `statuscode` | no flag; identified by `statuscode` |
| Status | `statuscode` | `statuscode` | `statuscode` |

**There is no "submitted" flag on any table.** Every event, including "submitted", is a `statuscode` value. The admin enters every status value that counts for each event, for example all statuses that mean submitted. These values are configurable per source and per trigger.

**Requirement wording.** An event trigger fires when `statuscode` moves from a value **outside** the configured set to a value **inside** it. A move between two values that are both inside the set does not fire again (e.g. Submitted → Under Review, when both count as submitted).

**The names above are as given; mixed case is the schema name.** Plugins use the lower-case logical name (e.g. `qdb_loanappl_type`). Confirm against the metadata at architecture.

## OQ-14 — Themes: DROPPED

**The user wants a GENERAL survey engine, not a theme-based question bank.**
- Questions are defined in the Form Engine designer (Form Type = Survey), organised in **pages** (tabs / wizard steps) and **sections**.
- AC2 themes (AC2.1, AC2.2a, AC2.4) and the theme-based option mapping are removed from scope.
- Answer types are those the Form Engine supports, not only Single / Multiple / Open text.
- Question order (AC3) is the designer's page / section / field order.
- OQ-14 is closed.

## Survey Category: DROPPED (correction 3 resolved)

**AC1.1 Survey Category (Milestone / Quarterly / Monthly / Annually) is removed. Triggers define the timing.**

A **Survey setup** has:
- one survey form (Form Type = Survey, `SRV-` code);
- one or more triggers of any kind (event, scheduled, milestone);
- channel (AC1.2);
- notification title and message (AC11/12);
- active from/to dates and expiry (AC13/14).

The quarterly expiry rule (AC14.1) applies to invitations generated by a quarterly scheduled trigger. This also answers OQ-09: a survey setup points to one survey form, so there is no separate question-set link.

## OQ-06 — Channel (partly answered)

- **Digital** = the customer portal.
- **Legacy** = the customer-service team created the request in CRM on the customer's behalf.

### Delivery: configurable per survey setup and per channel

**Delivery options for each channel (Digital / Legacy):**
- **Portal:** the survey appears in the customer's portal after login.
- **Secure link by email/SMS:** the customer answers without logging in.
- **No survey:** requests from that channel are not surveyed.

**Expected default:** Digital = Portal. Legacy = Portal, Link or None, as the admin chooses.

### Consequences to record in the BRD

1. **A secure link means an externally reachable page.**
   - It needs a single-use, expiring, unguessable token tied to one invitation and one customer.
   - No login is required, but it is NOT anonymous: the token identifies the customer.
   - This reverses BRD A-01 / constraint 3.3(c) for the link path.
   - It needs a security design (threat model) and PDPPL review.
   - On-prem orgs then need external exposure (OQ-13).
2. **Email/SMS sending must exist.** See OQ-07.

**Still to confirm at architecture:** which portal it is (technology and authentication), and how the Digital/Legacy origin is identified on each source request (which field).

## OQ-07 — Notification dispatch

- **SMS** goes through the **existing QDB SMS service**. The survey engine hands the message over and does not build its own gateway.
- **Email** is a CRM email activity, sent by the configured **Email Router** (on-prem, out of the box). The cloud org uses server-side sync.
- **Portal:** the invitation is visible in the portal (Digital channel).
- **Out of Scope change:** "email/SMS dispatch infrastructure" stays out of scope, because both already exist. Handing messages to them is now IN scope.
- **To confirm at architecture:** the hand-off contract of the QDB SMS service. In other QDB CRM work, SMS was sent by creating an activity record whose table differs per org, so the SMS table and columns must be per-org configuration.

**User confirmed:** the SMS table and fields are **configurable per org**, not fixed.

## OQ-08 — Results and reporting

**Results are viewed in CRM**, through views and charts per survey, per customer and per source request, plus Excel export.

**Storage must be Power BI-ready:**
- one Response row per invitation;
- one Answer row per question;
- the answers also stored as JSON.

**Power BI reports are NOT built in this project** and stay Out of Scope.

## OQ-02 / OQ-03 — Scheduled surveys

**Population is configurable per trigger:**
- all active customers; or
- customers with activity in the period (at least one record of a chosen source in the period), optionally filtered by status.

**Timing follows calendar dates:**
- Monthly: the 1st of the month.
- Quarterly: the 1st of Jan / Apr / Jul / Oct.
- Annually: 1 January.

There is no per-customer anniversary. Duplicate check: one invitation per survey + customer + calendar period. The fatigue rule applies (Postpone by default).

## OQ-11 — PDPPL and access

- **Retention period:** decided by **QDB Compliance**. It remains a hard release gate (NFR-008).
  - Build it as a **configurable retention setting**, with automatic deletion or anonymisation once Compliance sets the value.
- **Access:** a **dedicated security role** (e.g. "Survey Analyst") is required to read individual responses and answers.
  - Other users with access to the customer do not see answer content.
  - Admins configure surveys without needing read access to answers.
  - **New requirement:** define the security roles (Survey Admin, Survey Analyst) in the BRD.

## OQ-12 — Volumes (user estimate)

| Item | Volume |
|---|---|
| Active customers | ~450 |
| Disbursements | ~500 / month |
| Applications | ~200 / month |
| Fund transfers | ~200 / month |
| **Total source events** | **~900 / month** |

**Consequences:**
- Volume is low. Invitations can be generated directly by the async plugin, with no queue.
- The largest scheduled run is ~450 invitations (one per customer), well inside limits.
- With ~2 requests per customer per month, the **30-day fatigue rule will suppress most event triggers**.
  - The ceiling is ~450 surveys a month.
  - Expected: well under that.
  - The suppression log will show this. Admins should expect it.
- **Milestone N=5:** ~1.1 disbursements per customer per month gives about one milestone survey per customer every ~4–5 months.
- Section 9.2 volumes must be replaced with these figures.

## OQ-04 — "Record created" trigger: AVAILABLE

The "Record created" trigger is available to configure but is not used by default. It fires on record Create, optionally limited to the initial status values. The plugin is therefore registered on Create as well as Update for each source.

## OQ-13 — External access: the existing customer portal hosts it

- **The secure email/SMS link opens a token page inside the existing, internet-facing customer portal.** No new DMZ component, for on-prem or cloud.
- **Portal experience.** After login, the portal shows a **popup and/or an entry in the notification area**: "You have a pending survey". The customer answers there.
- **Delivery model, the same as the Form Engine.** QDB's own **frontend, backend and mobile teams** build the portal and mobile-app experience. MSS delivers the code they integrate:
  - the survey renderer (the Form Engine runtime, with Form Type = Survey);
  - the backend APIs / CRM Custom APIs: list pending surveys for a customer, get a survey (published JSON for the invitation's pinned version and language), submit a response, and validate a link token;
  - integration documentation.
- **Mobile app** is a consumer of the same APIs and renderer, so it is in scope as an integration target.
- **BRD impact:**
  - Add stakeholders: QDB frontend, backend and mobile teams.
  - Add FRs: the pending-survey API, popup / notification data, and token validation.
  - Building the portal / mobile UI itself is QDB's work and is Out of Scope for MSS. The integration package and documentation are In Scope.
