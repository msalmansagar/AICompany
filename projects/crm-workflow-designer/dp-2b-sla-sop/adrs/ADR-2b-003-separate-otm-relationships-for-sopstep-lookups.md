# ADR-2b-003 — Separate OTM Relationships for qdb_sopstep Lookup Fields

**Project:** DP-2b — SLA / Escalation on SOP Template Steps (CWFD)
**Status:** Accepted
**Date:** 2026-07-22
**Decided by:** Architect — Maqsad AI

---

## Context

The three escalation lookup fields on `qdb_sopstep`
(`qdb_escalation_user`, `qdb_escalation_team`, `qdb_escalation_role`)
require Dataverse One-to-Many (OTM) relationship definitions. These are
relationship-type attributes, not scalar columns; Dataverse creates
a `RelationshipDefinition` record for each one.

DP-2 created the same three lookup fields on `qdb_work_item_steps`, which
required three OTM relationships there:
- `systemuser` → `qdb_work_item_steps.qdb_escalation_user`
- `team`        → `qdb_work_item_steps.qdb_escalation_team`
- `qdb_role`    → `qdb_work_item_steps.qdb_escalation_role`

Each relationship has a unique `SchemaName` within the Dataverse environment
(not just within the entity). DP-2b must create three new relationships for
`qdb_sopstep` referencing the same three target entities. These cannot reuse
DP-2's relationship schema names because each schema name is global and uniquely
identifies a specific source entity → attribute pair.

---

## Decision

**Create three new OTM relationships for `qdb_sopstep` with distinct schema
names following the `qdb_[target]_qdb_sopstep_[field]` naming pattern:**

| Relationship schema name | Source entity | Source attribute | Target entity |
|---|---|---|---|
| `qdb_systemuser_qdb_sopstep_escalation_user` | `qdb_sopstep` | `qdb_escalation_user` | `systemuser` |
| `qdb_team_qdb_sopstep_escalation_team` | `qdb_sopstep` | `qdb_escalation_team` | `team` |
| `qdb_role_qdb_sopstep_escalation_role` | `qdb_sopstep` | `qdb_escalation_role` | `qdb_role` |

These are provisioned in `scripts/add-sla-sopstep-fields.js` via POST to
`/api/data/v9.2/RelationshipDefinitions` with `OneToManyRelationshipMetadata`.

**Navigation property names are NOT hardcoded in application code.** Both
adapters use `resolveNavProp('qdb_sopstep', 'qdb_escalation_user')` (etc.) to
discover the navigation property name from the Dataverse relationship metadata
at runtime. The result is cached per session. This is the same runtime-discovery
pattern used for all other lookup fields in the CWFD adapters.

---

## Alternatives Considered

**Reuse DP-2's relationship schema names (rejected):**
Attempt to add `qdb_escalation_user` on `qdb_sopstep` referencing the same
relationship definition as `qdb_work_item_steps.qdb_escalation_user`. Rejected:
Dataverse relationship schema names are globally unique. A schema name identifies
a unique relationship tuple (source entity, source attribute, target entity);
it cannot be shared across different source entities.

**Hardcode navigation property names (rejected):**
Pre-compute the expected nav prop names and hardcode them in the adapters rather
than querying `RelationshipDefinitions`. Rejected: navigation property names
are generated by Dataverse at relationship creation time and may not follow a
predictable pattern. Hardcoding creates a fragile coupling between application
code and schema metadata that breaks whenever the relationship is recreated.
The existing `resolveNavProp` pattern already solves this problem correctly.

---

## Consequences

**Positive:**
- Clean schema separation: `qdb_sopstep` owns its three lookup relationships
  independently of `qdb_work_item_steps`.
- `resolveNavProp('qdb_sopstep', 'qdb_escalation_user')` returns the correct
  nav prop name at runtime; application code is relationship-name-agnostic.
- The provisioning script pattern is identical to DP-2's, reducing implementation
  risk.

**Negative / Risks:**
- Three additional OTM relationship records in the Dataverse solution. This is
  a permanent schema addition; relationships cannot be deleted from a managed
  solution without removing the entire solution.
- The provisioning script must be idempotent on the relationship check:
  `GET /RelationshipDefinitions?$filter=SchemaName eq 'qdb_systemuser_qdb_sopstep_escalation_user'`
  before creating. If the check fails (network error), re-running the script
  must not create a duplicate. The script handles this by checking for HTTP 200
  on the existence query before issuing the POST.
- Relationship schema name correctness must be verified by the Phase 4 developer
  in a dev org before running in production; incorrect names are difficult to
  rename post-deployment in a managed solution.
