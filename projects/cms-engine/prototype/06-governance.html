🛡
Written by the plugin, never by the browser. If the designer wrote both the version and the log, an author could keep the write and drop the log — devtools, blocked request, done. Routing publish through qdb_PublishPage makes the log structurally unavoidable: the same call that goes live writes the row.

Stated honestly: this guarantees "no page went live without a log". It does not guarantee "nobody changed content another way" — a user with direct table access can still write through the Web API. Dataverse security remains what governs that.
👤
Roles map onto Dataverse security roles — the CMS adds no parallel permission system. Shell editing is separated from content editing on purpose: an author who can delete the navigation can break every page at once, so that privilege sits with Portal Admin alone.

Why the shell is gated

Header, navigation and footer are editable regions like any other — which means an author could delete the navigation and break every page at once.

Until shell versions can be rolled back independently of page content, shell editing stays with Portal Admin. Content Authors get the middle region only. That is a deliberate sequencing decision, not a platform limitation.
