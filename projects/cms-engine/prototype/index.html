QDB CMS Engine

A UX prototype for a metadata-driven content management engine that runs inside Dynamics — a Dataverse web resource for the designer, a plugin for anything that must be auditable, and no hosted middle tier. Same architecture as the Report Engine (ADR-RPT-011). 15 screens across seven files, one design system.
🔓
Everything here is a screen, not a code change. A Power Admin can build components, define fields, approve colours, upload icons, edit navigation and publish — with no developer involved. Capability is governed by permission, not by who can write code. A developer is only needed to add a genuinely new kind of brick, which is rare.
⚠️
Serve over http, not file:// — the shared scripts will not load otherwise. From this folder: npx serve . or python -m http.server.
ℹ️
Field names throughout match the Dataverse schema the engine would really use — qdb_cmspage, qdb_cmspageversion, qdb_cmspublishlog, qdb_PublishPage — so the prototype and the eventual build describe the same system. Use the theme toggle in the top bar for dark mode and the locale picker to flip the designer canvas to Arabic RTL.

The three decisions this prototype is arguing for

Publish is a plugin

Not a browser write. If the designer wrote both the version and the audit row, an author could keep the write and drop the log. Routing publish through qdb_PublishPage makes the log unavoidable — the same call that goes live writes it.

Colour is a token slug

Authors never see a colour picker. Only approved colours can reach a page, and a rebrand — or a per-service palette — changes token values with no page edited and nothing deployed.

One tree, two languages

English and Arabic live on the same node, not in separate trees. Structure is shared by construction, so a missing translation shows as a missing string rather than as a different page.

What keeps it safe

Handing this much power to non-developers only works because three things exist, and all three are in the prototype: approval before publish, so an author cannot reach a citizen alone; versioning, so every change is a new version and anything can be rolled back; and an audit log written by the plugin, so it cannot be skipped. Remove any one and "everyone can do everything" becomes "anyone can break the public site".

Not in this prototype

No real Dataverse connection and no authentication. Photography is represented by CSS gradients, and the Arabic copy has not been reviewed by QDB. The component builder shows the flow but does not persist what you build.

The Designer is the exception — it runs the real Puck editor, loaded from a CDN. It is the only screen here that needs a network connection; every other screen works offline. In production Puck ships bundled into a single Dataverse web resource, because a hardened CRM blocks CDN loads.
