# FORM ENGINE — On-Premise Deployment Kit (Dynamics 365 CE 9.x on-prem)

Two artifacts, deployed in the order below. The solution does **not** contain the
plugin — the plugin is registered separately.

| # | Artifact | What it carries | How to deploy |
|---|----------|-----------------|---------------|
| 1 | `Qdb.FormEngine.Plugins.dll` | Custom API implementations `qdb_PublishForm`, `qdb_GetPublishedFormJson`; translation-change step; publish workflow activity | Plugin Registration Tool |
| 2 | `FORM_ENGINE_unmanaged.zip` | 34 `qdb_*` entities, 47 web resources (runtime `qdb_form_runtime.html`, the form designer bundle, icons), Custom API **definitions**, sitemap, app actions | Solution import |

`MissingDependencies` in the exported solution is **empty** — it is self-contained.

---

## Why the plugin is mandatory
The runtime renders published forms by calling two Custom APIs:
- `qdb_PublishForm` — regenerates the render cache when a form is published.
- `qdb_GetPublishedFormJson` — returns the published form JSON to the runtime.

The solution ships the Custom API **definitions** but not their code. Without the
DLL registered and bound, both APIs are inert and no form will render.

---

## Deployment order (important — Custom API ↔ plugin-type binding)

Plugin-type GUIDs differ between the cloud org and your on-prem org, so the Custom
API records that arrive in the solution will reference plugin-type IDs that do not
exist on-prem. Handle it in this order:

1. **Register the plugin first.**
   - Open Plugin Registration Tool → connect to the on-prem org.
   - Register New Assembly → `Qdb.FormEngine.Plugins.dll`.
   - Isolation: **Sandbox** (or None/full-trust if your on-prem policy requires it).
   - Location: **Database**.
   - This creates the assembly and its plugin types (PublishForm, GetPublishedFormJson,
     TranslationChange).

2. **Import `FORM_ENGINE_unmanaged.zip`** (Settings → Solutions → Import).
   - Creates entities, web resources, and the Custom API definitions.

3. **Bind the Custom APIs to the on-prem plugin types.**
   - In Plugin Registration Tool, view the Custom APIs `qdb_PublishForm` and
     `qdb_GetPublishedFormJson`.
   - Set each one's **Plugin Type** to the matching type from the assembly registered
     in step 1 (the cloud GUID will not resolve on-prem — rebind by name).
   - Confirm the request parameters / response properties match
     (`FormCode`, `TargetVersion`, `PublishJobId` for PublishForm).

4. **Register the non-CustomAPI steps** (if not already carried):
   - Translation-change step on `qdb_translation` (from `TranslationChangePlugin`).
   - Publish workflow activity `PublishFormActivity` (if you use the workflow path).

5. **Publish All Customizations.**

6. **Smoke test:** publish a form (fires `qdb_PublishForm` → row in
   `qdb_form_render_cache`), then open the runtime web resource `qdb_form_runtime.html`
   and confirm it renders.

## Known on-prem risks

- **Package version 9.2 → on-prem 9.x.** This package was exported from cloud build
  `9.2.26062` with `SolutionPackageVersion="9.2"`. On-prem 9.0/9.1 may refuse a package
  from a newer build ("exported from a newer version of Dynamics 365"). If import fails
  on that check, the package version in `solution.xml` can be down-levelled and repacked —
  ask and I'll produce a 9.0/9.1-stamped variant.
- **Custom API on-prem.** Custom APIs require D365 CE **9.0+**. Confirmed target is 9.x, so
  supported — but they must be bound to the on-prem plugin types (step 3).
- **Web-resource size.** `qdb_form_runtime.html` is ~1.9 MB and the bundled
  `qdb_workflow-designer` html ~1.7 MB. Default on-prem max web-resource size is 5 MB; no
  change needed, but note it if your org lowered that limit.
- **Runtime web resource is a build artifact.** If you later change the frontend, rebuild
  `qdb_form_runtime.html` (`vite build --config frontend/vite.webresource.config.ts`) and
  re-import / re-upload — it is not regenerated by the plugin.

## What is NOT in this kit
- The Node/Fastify backend API — not required for the in-CRM runtime path (the plugin +
  render cache serve forms inside Dynamics). Only needed for the external portal/mobile.
- Seed data / demo forms — create forms with the designer, or run the seed scripts against
  the on-prem Web API.
